# Capsaicin: Micro-World task, RoboJEPA adaptation

The target is first-frame + keyboard/mouse controlled **video generation**, following [Micro-World 2](../../vendor/micro_world). Data preparation, the GPU gate, all four latent shards and the 2,000-update predictor action-interface run are complete. The selected predictor is step 1,600; final held-out and action-control metrics are in [reports/train.json](reports/train.json). RGB generation and the original video metrics remain incomplete; predictor training is not a completed video-generation benchmark. Read [REFERENCE_AUDIT.md](REFERENCE_AUDIT.md) for the source comparison.

## Data and actions

Preparation requests 2 CPUs and 8 GB RAM, reuses the existing nanochat container, and builds the locked video runtime once. Weight downloads and tar packing are streamed; the 30 GB encoder checkpoint is never loaded/rewritten by this CPU job. The already-queued GPU gate (48 GB host RAM, 160 GB scratch) extracts `target_encoder` once and publishes the compact shared weights archive. All four encoding jobs reuse it.

Only the fixed `200f/video/` and matching `200f/metadata-detection/` files from `amd/Micro-World-Capsaicin` are downloaded. The 440 clips occupy about 0.95 GB. Raw JSON is retained. Correct W/S once in memory using the upstream marker, then **call `VideoGameDataset._actions_to_tensors` directly**. Compare every clip's result against the small stdlib port before caching it.

Actions are incoming-frame controls: row `i` describes motion into frame `i`; the first frame has zero control. A transition from cached frame `l` to `r=l+4` consumes rows `l+1` through `r`, in order. Each row has W/S/A/D/jump/sneak/sprint/pitch/yaw; four rows give 36 values, padded to RoboJEPA's 64 slots. Mouse values use the upstream factor × 15 conversion into **degrees**. No extra inference-time pitch flip is applied.

`process_collisions=True` matches the reference trainer: collision clears movement labels and invalid jump clears `scs`. These are **processed control labels**, not guaranteed raw player commands; collision outcomes affect the labels even though they are not separate input channels. This corrects the previous incompatible claim that outcomes never affected inputs.

Use the reference stage-2 default 352×640 center crop, then downsample to 176×320 for the single-GPU preflight. ImageNet normalization and independent-frame V-JEPA 2.1 encoding are JEPA-specific changes. Cache every fourth frame, layer-normalized, BF16: about 16 GB. Raw 200-frame action rows remain in each cache for exact temporal-window/reversal processing. Schema 2 rejects the old shifted-action cache.

The source trainer samples 81-frame windows. Our windows cover the same 80 transition frames using 21 cached states; starts are restricted to stride-4 boundaries. The 0.5 temporal-reversal augmentation calls the upstream coupled frame/keyboard/mouse function, only for no-jump windows. Evaluation never augments.

Our conservative asset-family split is **not an upstream published benchmark split**. It groups camera/anchor variants into eight families: bistro, gallery, sponza, suntemple, hidden_alley, namaqualand, the_shed, verdant_trail. With seed 42: train 332 clips, validation 20 (sponza), test 88 (namaqualand). Unknown filenames fail rather than silently becoming new scenes.

## Model and evaluation

Load the official 100M predictor strictly, retaining all old parameters and adding a Capsaicin embodiment. Follow Micro-World's action-stage freezing strategy: freeze the encoder and predictor trunk; update only the new action projection/bias, task embedding and zero-proprioception bias. Gradient masks protect old embodiment rows. Weight decay is zero because the parameters share tables with frozen embodiments; the GPU gate verifies exact old-row/trunk preservation.

Keep RoboJEPA's MAE latent objective; cosine is diagnostic. The prior extra cosine penalty was removed. Teacher-forced prediction uses overlapping windows of at most 16 states; a two-step differentiable rollout starts from **one observed frame**. Longer rollouts slide a 16-state context; this is an explicit positional-context adaptation, not Micro-World's Wan KV-cache implementation.

Latent preflight reports 1/2/5/10/20-step errors, corresponding to 4/8/20/40/80 source-frame offsets, plus persistence and action sensitivity. These do not establish RGB quality or physical correctness. The eventual video task needs matched generated/reference videos, action-controllability evaluation and the visual/temporal metrics under upstream `test_metrics`. See `evaluation-protocol.json` for the incomplete task contract.

## Selected RGB decoder

The default RGB path reuses the pretrained V-JEPA2 decoder from [JEPA-WMs](https://github.com/facebookresearch/jepa-wms), with checkpoint [`facebook/jepa-wms/vjepa2_vitg_256_INet.pth.tar`](https://huggingface.co/facebook/jepa-wms/blob/main/vjepa2_vitg_256_INet.pth.tar). RoboJEPA remains the encoder and action-conditioned predictor.

The interface is `RoboJEPA features (1664) -> Linear(1664, 1408, bias=True) -> pretrained JEPA-WMs decoder -> RGB`. The adapter has 2,344,320 parameters. The decoder retains its pretrained input projection, 1024-wide internal representation and 12 transformer blocks (about 153M trainable parameters). Reference the upstream [`VisionTransformerDecoder`](https://github.com/facebookresearch/jepa-wms/blob/main/app/plan_common/models/decoder.py) and [V-JEPA2 decoder training configuration](https://github.com/facebookresearch/jepa-wms/blob/main/configs/vjepa_wm/vm2m/open_source_decs/step2_lpips_vm2m_vjepa2vitgopen_vgxf_vitldec_dup_256_vjtransf_norm_bs4_4n.yaml); pin the source and checkpoint revisions when integrating them.

For decoder training, freeze the RoboJEPA encoder and predictor. Reuse the cached real-frame features and their matching RGB targets, briefly warm up the adapter, then fine-tune the adapter and decoder with the upstream L2 pixel and LPIPS perceptual losses. This learns feature-distribution alignment as well as the channel mapping. Adapt the upstream square-grid resizing, positional encoding and pixel-patch assembly to the 176×320 output, preserving the pretrained learned weights. Evaluate real-latent reconstruction before predicted-latent rollouts, including temporal stability on the existing held-out scenes. Framewise decoding retains the cache's stride-4 cadence; it does not itself restore the original video frame rate or establish real-time throughput.

The implementation is in `robojepa_worlds/rgb_decoder.py`, reusing the pinned `vendor/jepa_wms` attention blocks and complete pretrained decoder. The adapter is randomly initialized, so meaningful RGB requires training; dimensional projection alone does not align the feature distributions. `decoder_gate.py` first updates only the adapter for 16 steps, then jointly updates adapter/decoder for 48 steps on four fixed training frames. This bounded overfit check verifies learning and interfaces, not full-data reconstruction quality. It does not create W&B runs or retain diagnostic model weights. The short-fit images/video must not be presented as final model quality.

The gate checks strict checkpoint loading, square-output parity with the original decoder, rectangular output shape, frame independence, frozen decoder preservation during warmup, finite nonzero gradients, same-state optimizer/RNG recovery and improvement of fixed-frame reconstruction. The selected predictor remains frozen and must give identical output before/after decoder adaptation. A held-out three-column diagnostic video shows source RGB, decoded real features and decoded predictor features at the original stride-4 timing. GPU validation is recorded in `reports/decoder-gate.json`.

The checkpoint predicts ImageNet-normalized RGB, which is inverted before the pixel loss. The upstream `WorldModelViTImageHead.compute_loss` then sends [0,1] RGB to LPIPS without its normalization option. We explicitly correct LPIPS inputs to [-1,1], while preserving the selected objective `10*MSE(RGB in [0,1]) + LPIPS`: reuse the upstream loss with pixel coefficient 10/4 after range conversion. VGG LPIPS and logvar are frozen; there is no discriminator. Outputs are clamped only for display/clipped PSNR, not for optimization. The gate numerically checks this loss formula. Import aliases isolate JEPA-WMs' `src` modules from RoboJEPA's modules; no upstream files are edited.

The decoder adds only `lpips==0.1.4` to the locked environment in `decoder_env/`; the original predictor environment/cache remains reusable. `python3 -m cluster.decoder_submit` submits exactly one held-reviewed H100/H200 diagnostic (4 CPUs, 16 GB RAM, 100 GB scratch). It downloads the revision-pinned 1.84 GB decoder and 0.55 GB VGG assets on the compute node and publishes shared decoder assets/runtime for reuse. `python3 -m cluster.watch_decoder` collects its report and exits on completion or failure, without submitting further jobs. The decoder job root is `/home/yzhong239/robojepa-capsaicin-jobs/decoder/gate`.

Decoder debugging now uses one explicitly interactive GPU allocation (`condor_submit -i`), with transferred runtime/data reused throughout the session. Source `decoder_debug.sh` from scratch, run `decoder_prepare_session`, then `decoder_run`. The latter runs the bounded check under `pdb`: exceptions retain the live model/optimizer and traceback for inspection; fixes can be tried in the same allocation. `decoder_activate` selects the transferred environment, and `decoder_save` archives small reports plus the edited source (no model weights). Do not restart the former batch gate/collector automatically. Debugging remains separate from formal decoder training and W&B.

The complete 64-update check now passes on A100 40 GB (`reports/decoder-gate.json`). Interactive diagnosis confirmed exact restoration of model, optimizer and RNG, but nondeterministic default backward kernels caused a 3.87e-6 next-update parameter difference. Enabling strict deterministic algorithms and deterministic cuDNN produced zero loss, gradient and parameter differences, without changing recovery thresholds. The full short fit used 4.98 GB peak PyTorch allocation and 29.4 seconds after initialization began; fixed-frame reconstruction loss fell from 1.565 to 0.607. These four-frame results and the exported rollout are diagnostic only; held-out RGB remains coarse and shows patch artifacts. The full-data training protocol is described below.

The authorized full-data decoder run uses `decoder-train.json`: 5,000 updates / at most six training hours, 200 adapter-only updates followed by joint adapter/decoder tuning. Four shuffled clips supply up to four frames each per update, using weighted gradient accumulation; all 16,600 training frames occur exactly once per epoch (1,079 updates), including the short final batches. The 5,000-update limit corresponds to 76,928 frame presentations, or 4.63 frame epochs. Adapter/decoder learning rates start at 1e-3/1e-5 with a brief adapter LR warmup and cosine decay in the joint phase. The decoder optimizer is rebuilt at the phase transition, as in the validated short fit. Encoder and predictor remain frozen; training reads cached real features and paired RGB.

Submit with `python3 -m cluster.decoder_train_submit`. The worker reuses the prepared locked environment and assets, starts from the official pretrained decoder and a fresh adapter, logs a separate formal decoder run in `yibozhong657-none/robojepa-capsaicin`, and persists model/optimizer/RNG/data position/phase via the existing 1,800-second exit-85 protocol. Latest and best are separate inside one overwritten checkpoint archive on staging. Full development reconstruction evaluation runs every 500 updates; the best development-loss checkpoint receives final full development/test evaluation and a frozen-predictor rollout video. `python3 -m cluster.watch_decoder_train` exits after observing the first finite formal update and never resubmits failures.

## Frozen control and long-rollout evaluation

`control-eval.json` / `robojepa_worlds.control_eval` reuse predictor run b27dd2b1 step 1600 and decoder run 1e866f14 step 5000 without updates or W&B. Four anchors are fixed before inspection: indices 0 and N//2 in each held-out split. Each produces 100 steps under recorded-then-zero, zero, forward, backward and signed-yaw controls. The yaw magnitude is the training-only median absolute nonzero source-frame yaw in degrees. Controls retain Micro-World's incoming-frame convention and four ordered source controls per 64-dimensional action chunk.

The recurrence is the existing 16-state sliding window, with framewise RGB output. Recorded-trajectory metrics at horizons 1/5/10/20/40 compare predicted-latent decoding, real-latent decoding and RGB persistence against the same ground truth. Six-panel videos and per-horizon differences from zero controls expose sensitivity and drift; they do not establish physical or directional correctness, because counterfactual simulator ground truth is unavailable. Only 49 recorded transitions exist, followed by zero input. This four-anchor diagnostic is not an upstream benchmark score or proof of real-time streaming. `cluster/control_eval_debug.sh` runs it inside one explicit interactive GPU allocation, retaining the session on errors; the compute limit is 900 seconds.

## Execution

`python3 -m cluster.submit prepare` submits preparation. Pre-submit the GPU gate with `python3 -m cluster.submit gate --defer`, then each of the four encoding jobs with `python3 -m cluster.submit encode --shard N --defer` (N=0..3). These jobs enter the real Condor queue held on their dependencies; they do not reserve a GPU while waiting. `python3 -m cluster.workflow` releases the same job IDs after successful dependencies, collects reports, and exits after all four encoding shards finish because `auto_train=false`. Artifact sizes, source compatibility and the GPU gate are checked before release; an unexpected hold/failure stops the workflow.

The explicitly authorized predictor run uses `formal=true`, while `auto_train=false` keeps the preparation controller from creating training runs. Submit once with `python3 -m cluster.submit train`; the state/intent/lock and queue checks prevent duplication. Only execution metadata changed in `pilot.json`; the model, objectives, data processing, optimizer, checkpoint recovery and numerical configuration retain the successful GPU gate implementation. Validation compares all configuration keys except `formal`, `auto_train` and `milestone`, so scientific changes still invalidate the gate. Training requests one complete H100/H200, 4 CPUs, 16 GB RAM and 100 GB scratch, including the container, archives, extracted features and checkpoints. After one continuous idle hour the existing cu126 SDPA backend permits A100 80 GB fallback, retaining H-card preference; Blackwell is not enabled.

`python3 -m cluster.watch_train` watches this job until a finite formal update appears after its run-specific start marker, then exits. It never submits a job or restarts a failure. HTCondor resumes the same job/run ID from persistent `checkpoints.tar` and `results.tar` after each 1800-second exit-85 segment. Local monitor records live under the job's `train/` directory; only actual finite steps count as training started.

GPU validation covers real pretrained tensors, upstream action/reversal parity, causality, action gradients, frozen-weight preservation, an 81-source-frame training window, 20-step rollout and numerical checkpoint recovery. Static checks cannot substitute for this gate. The earlier full-predictor plus random-predictor pilot is not automatically launched.

The existing 2,000-step / 6-training-hour ceiling remains unchanged. When the RGB task path is implemented, the shared training/recovery code retains optimizer, RNG, sampler position and run ID; latest/best are separate and archive failure cannot return exit 85.
